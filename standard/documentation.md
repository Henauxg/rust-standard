# Documentation and comments

## Doc comments

### Document every public item of library code

In library code, every public item has a doc comment, and the crate enables
the `missing_docs` lint:

```toml
# Cargo.toml of a library crate
[lints.rust]
missing_docs = "deny"
```

Its users read the documentation without the source, such as on docs.rs.

In application code, an item gets a doc comment only where it says something
its name and signature do not.

### Write doc comments that add something

- Cover enough of the crate with examples, somewhere, to show how it works.
  Not every function needs one.
- Document every case where a function panics on bad input. Under the
  no-panic rule ([api_design.md](api_design.md#do-not-panic)) these are rare.
- Document the invariants of unsafe functions and traits.
- Write sentences, with capitals and punctuation.
- Do not explain the language:

  ```rust
  struct MockFileSystem { ... }

  // Bad: says what `impl FileSystem for MockFileSystem` already says.
  /// A mock implementation of the FileSystem trait, intended to be used in unit tests.
  impl FileSystem for MockFileSystem
  ```

- Do not repeat the name. With nothing useful to say, leave the comment out,
  and allow `missing_docs` on that item if it is library code:

  ```rust
  // Bad
  /// Removes an element.
  pub fn remove_element() -> Element {}
  ```

- An enum's variants may go undocumented when their names explain them.

### Format doc comments as Rust does

- `///` documents the item that follows: a function, a struct, an enum, a
  trait, a type alias.
- `//!` documents the module or the crate, at the top of its file.
- Follow the [Rust Style Guide on doc comments](https://doc.rust-lang.org/nightly/style-guide/#doc-comments),
  and write them in Markdown.
- Write documentation directly with `///` and `//!`, not generated by a macro,
  so it reads in the source.

Doc comments and ordinary comments may be mixed: one thing for users of the
item, another for whoever changes it.

```rust
/// Finds the first `FooItem` with the given `name`, or `None` if not present.
// TODO(#123): `name` should be a `&str`, not a `String`.
pub fn get_named(items: &[FooItem], name: String) -> Option<&FooItem> {...}
```

Rust gives doc comments a syntax of their own, which tools rely on: rustdoc
and editors read them, they follow Markdown, a doc comment put where it cannot
document anything is linted, and macros can produce and read them.

## Code comments

### Comment only what the code cannot show

Use `//` for everything that is not documentation. Most code needs no comment.
A comment says what the code cannot: a constraint, a measurement, a trap.

- Write in the present tense. No history, dates or incident stories, and no
  "this used to be X": the history is in `git log`.
- Keep a comment shorter than the code it explains, as a rule of thumb. A dense
  line may need more.
- Write plainly: the point first, one idea per sentence, common words, no em
  dashes. The same applies to doc comments.

### Track a TODO with an issue

A TODO names the GitHub issue that tracks it: `// TODO(#123): what remains`.
A TODO without an issue is not committed.
